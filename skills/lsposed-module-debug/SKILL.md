# LSPosed 模块 App 真机排查

适用：模块注入失败（App 报「系统服务注入失败」之类）、模块 App 自身闪退、hook 分支疑似未生效。

## 步骤

1. 先拿崩溃栈：`adb devices` 确认设备，再 `adb logcat -d -b crash -t 40` 读 Java 栈——异常类型 + 出错文件行号直接给根因方向。完成：写出异常类与出错行。

2. 抓 App 自身日志：`adb shell pidof <pkg>` 取 pid，再 `adb logcat -d --pid=<pid>`（或 `-s <Tag>`）。系统日志（如 OplusGeocoderProxy）会刷爆主缓冲，按 pid/tag 过滤才看得见。进程日志有配额，关键行会被丢（`LOG_FLOWCTRL ... DROPPED`）：把关键数据临时写进 `filesDir` 再用 `run-as <pkg> cat` 读，取到后再删。完成：确认 App 实际执行到哪一步、哪条日志缺失。

3. 取 LSPosed 日志：`adb shell su -c "cp /data/adb/lspd/log/modules_*.log /data/local/tmp/m.log"` → `adb pull` → 本地 grep。设备上 `su -c grep "带空格模式"` 会被拆词报错，一律拉回本地再搜。用模块自己的 tag 标记（各分支入口的 Logger.info）判断进程里走了哪条分支。`verbose_*.log` 比 logcat 更持久（logcat 缓冲滚过就没了），且 `injectLocation success!` 行会打印注入后的完整 `Location`，含 extras 的每个键值——要核对 hook 实际往外暴露了什么数据（如 `portal_speed`/`latlon`），直接读它：`ls -t /data/adb/lspd/log/` 取最新，或 `grep -h 'injectLocation' /data/adb/lspd/log/verbose_*.log`（模式不带空格，避开设备侧拆词）。**日志会轮转**：重装 APK、重启 App、reboot 后 LSPosed 新建 `verbose_<时间戳>.log`，沿用旧路径 tail 只会读到旧时间戳，把「新进程还没注入」误判成修复失败——每次验证前重新 `ls -t /data/adb/lspd/log/verbose_*.log | head -1` 解析路径。完成：确认模块在目标进程是否加载、走了哪条分支。

4. 查模块启用与作用域：pull `/data/adb/lspd/config/modules_config.db` 及 `-wal`、`-shm` 三个文件，用 python3 sqlite3 读 `modules_state`(enabled) 和 `scope`(module_pkg_name, app_pkg_name)。完成：确认模块已启用、目标进程包在 scope 内。

5. hook 分支判定坑（务必）：`XC_LoadPackage.LoadPackageParam.appInfo` 在 system_server（包名 `android`）可能为 null。只按 appInfo 判「系统应用」会把 system_server 当用户应用：装上客户端 hook 后提前 return，框架侧 hook（LocationServiceHook 等）全不装 → App 的 extraCommand 无人应答，界面报「系统服务注入失败」。判定要显式加 `packageName == "android"`、`processName == "system"` 和已知系统包（com.android.phone、com.android.location.fused、com.xiaomi.location.fused、com.oplus.location）。完成：LSPosed 日志出现系统分支的入口标记，且 system_server 不再出现客户端 hook 日志。

6. Kotlin data class JSON 坑（务必）：fastjson2 的 `JSON.parseArray/parseObject(json, X::class.java)` 在 Android 上取不到 Kotlin 构造参数名，反序列化把非空参数传成 null，抛 `NPE: Parameter specified as non-null is null: X.<init>, parameter name`；**JVM 单测会通过**，只有真机复现。改为 JSONArray/JSONObject 手工读写，并对脏条目跳过而非抛异常。完成：真机打开该页面不再崩溃，回读数据与写入一致。

7. 生效方式：xposed 侧改动必须重启（LSPosed 只在进程启动时注入，system_server 无法单独重载）——`adb reboot` 后轮询 `adb shell getprop sys.boot_completed` 直到为 1 再验；仅 App 侧改动重装 APK 即可。完成：重启后日志出现修复后的分支标记。

8. 无 UI 自动化时驱动界面：`adb shell uiautomator dump /sdcard/ui.xml` → `adb pull` → 本地 grep `resource-id`/`text` 取 bounds → `adb shell input tap X Y`；每步 dump 确认再点（抽屉动画期间点击会落空）。预置状态：先 `am force-stop`，再写该 App 的 prefs 并重启 App。**LSPosed 模块 App（manifest 声明 xposedsharedprefs）的 SharedPreferences 不在 `/data/data/<pkg>/shared_prefs/`**：LSPosed 把整个目录重定向到 `/data/misc/apexdata/<UUID>/prefs/<包名>/`（SELinux 标签 `lsposed_file`），写 `/data/data/...` 不报错但完全不生效。定位真实路径：`adb shell su -c "am dumpheap <pid> /data/local/tmp/h.hprof"` → `adb pull` → python 搜 `portal.xml`（HPROF 里 ASCII 串按 UTF-8 字节存，非 ASCII 在 char[] 里按 UTF-16BE 存）。改写用 `su -c "cat /data/local/tmp/new.xml > <真实路径>"` 就地覆写，保住 owner 与 SELinux 标签（别用 cp 新建）。改包名或重装应用会换到全新 prefs 目录，旧设置（如循环广播开关）静默回默认值——用户报「提示成功但没效果」先查这里。勾选态验证：PopupMenu 菜单项的标题 TextView 恒为 `checkable="false" checked="false"`，真实勾选状态在它的兄弟节点 `android:id/checkbox`（`checkable="true"`）上——按 `checkable="true"` 抓节点读 checked，别按标题文本判断，否则会把「已勾选」误读成未勾选。完成：dump 中出现目标页面的文本，且改写 prefs 后 App 行为随之变化。模块的悬浮摇杆是 `TYPE_APPLICATION_OVERLAY` 窗口，`uiautomator dump` 里根本没有它——位置得从 `adb shell dumpsys window windows | grep -A20 "<pkg>"` 的 `frame=[l,t][r,b]` 取；`RockerView` 固定 400px 方形（`DEFAULT_SIZE`），中心 ≈ (l+214, t+214)，`adb shell input swipe <中心> <中心-250> 800` 即可触发 `move`。验证「移动中」的 `speed`/`mov` 必须在 swipe 后**立即**读日志：`FakeLoc.isMoving` 是「最近 2 秒内有坐标改变」，晚几秒就回落成 `vel=0.0 mov=false`，容易误判成「没触发」；先看 `bear` 是否变化可确认 move 真发生过（`move` 与 `update_location` 都算坐标改变）。完成：日志出现 `mov=true` 且 `vel` 落在 `spd` 附近。

9. 判定 hook 是否真生效（用户报「App 说成功但没效果」时必查，别先改代码）：打开 App 调试开关（写 prefs `debug=true` 并重启 App，让它 `put_config` 下发 `FakeLoc.enableDebugLog`），再 `adb logcat -d | grep -E "commandId=|injectLocation success"`。出现 `commandId=update_location, rely=Bundle[{lat=..., lon=..., mode==}]` = App→hook 指令到达且坐标正确；出现 `injectLocation success! Location[fused ...]` = 注入确实发生。两条都在而目标 App 仍拿不到位置，就别动注入链路，转查目标 App 是否在 scope、是否走 FusedLocationProvider。完成：用日志分别坐实「App 侧发送」与「hook 侧注入」两段。坑：App 侧的循环广播线程随进程存活，重装 APK 或重启 App 后不会自恢复——需在界面把模拟关一次再开，否则 `injectLocation` 计数停在 0，会把「已修复但没拉起」误判成修复失败。

10. 删 Gradle 依赖后的运行时回归：源码 grep 无引用 ≠ 运行时不使用——`app/libs/*.jar` 厂商 SDK（如 BaiduLBS_Android.jar）运行时会用 okhttp 等可选依赖，删掉后 `:remote` 进程抛 `NoClassDefFoundError: okhttp3/OkHttpClient$Builder`，且 ColorOS 记该 App 为 unstable 后 `prevent restart service`。删依赖后必须真机跑一轮 `adb logcat -d -b crash -t 40`，见 `ClassNotFoundException`/`NoClassDefFoundError` 就恢复该依赖重建。完成：crash 缓冲不再出现该类异常。

11. 对外暴露面审计（用户问「目标 App 能否检测到本模块」时）：先枚举跨进程传给目标 App 的数据——`extras?.put`、`putExtra`、`System.setProperty`、`sendExtraCommand` 的 provider 名、manifest 的 `xposed*` meta-data（包名/meta-data 类若已由 HMA 隐藏应用列表覆盖，不在本步范围）。**`location.extras` 随 Parcel 到达每个拿到该 Location 的应用**，含模块名的键就是指纹：无读取方的键（`latlon`）直接删，有读取方的改中性键名（`portal_speed`→`spd`）并只在对应功能开关开启时写入（`if (FakeLoc.sensorMockEnabled)`），读取方常量同步改。进程级去重别用 `System.setProperty`（同进程代码可枚举属性名），改模块内静态 `Set`。被开关包住的写入要先用日志确认是否真出现（`portal.enable` 在 `hideMock=true` 时从未写入）。provider 名与指令通道先读鉴权（`BinderUtils.isLocationProviderEnabled` 只放行 uid<10000 或包名全含模块名的调用者，第三方探测得 false），确认是真暴露再动。验证走第 7 步重启流程，读 `injectLocation success` 行的 extras 核对。完成：旧键消失、新键值正确。区分「指纹」与「数据不合理」（`bAcc` 等于 bearing 值、speedAccuracy 塞模拟速度）：后者改的是对外数据语义，先报告再改，别混进同一次提交。修这类值：`bearingAccuracyDegrees` → `Random.nextDouble(1.0, 5.0)`（四个注入点必须同改：BaseLocationHook、BasicLocationHook、LocationProviderManagerHook 两处，后两个文件没有 Random 导入要补）、`speedAccuracyMetersPerSecond` → `Random.nextDouble(0.1, 0.5)`、`location.speed` 加 `coerceAtLeast(0.0)`（抖动会压出负值，实测 `vel=-1.449`）。验证只认日志打印的字段：`Location.toString()` 不含 speedAccuracy，别据日志宣称该字段已验证——以 `bAcc` 落在 1~5、`vel` 全正、extras 键正确为完成判据。设备侧 `su -c "grep -h '带空格模式' 文件"` 会被拆词：报一行 `grep: <第二个词>: No such file or directory`，同时把「只匹配第一个词」的结果当成功输出——要精确匹配就把日志 pull 回本地再 grep。

12. release 构建的日志钳制（用户要求「release 包不产生 debug 日志」时）：library 模块默认不生成 BuildConfig，需在 build.gradle.kts 加 `buildFeatures { buildConfig = true }`；日志总开关（`FakeLoc.enableDebugLog`）getter 改为 `配置值 && BuildConfig.DEBUG`（setter 写私有 backing var，所有赋值点不用改），release 恒 false——远程指令也翻不开；`Logger.debug()` 自身加开关守卫（原实现不查开关、全靠调用方 if，漏网调用会直接输出）。验证：`xposed/build/generated/source/buildConfig/release/.../BuildConfig.java` 的 `DEBUG=false`、`aapt2 dump badging` 无 debuggable、native lib 明显小于 debug（strip 生效，实测 libportal.so 1.96MB→1.58MB）。坑：**release 构建会跑 lint，debug 不会**——删默认 strings 后其他语言文件（values-ja 等）残留翻译会让 `lintVitalRelease` 报 ExtraTranslation，删字符串要连同全部 `values-*/strings.xml` 一起清。

13. 开 R8（`isMinifyEnabled=true`）后的 keep 与验证：混淆会按名反射失败或删掉入口，至少写 `-keep class <xposed_init 入口类> { *; }`、`-dontwarn de.robv.android.xposed.**`（API 是 compileOnly），再加 `-keep,allowoptimization class <模块包>.** { *; }`。坑（实测踩过）：R8 的 library classpath 不含 compileOnly 的 Xposed API，所以 `-keepclassmembers class * extends de.robv.android.xposed.XC_MethodHook { *; }` 这类靠父类匹配的规则**匹配不到任何类**，R8 把 `beforeHookedMethod`/`afterHookedMethod` 当无人调用的方法删掉 → 模块照常加载、日志无报错，但所有 hook 变空壳（App 报「系统服务注入失败」）；`allowoptimization` 保住成员与类名、仍允许常量折叠，实测调试字面量计数仍为 0。判定 keep 是否真生效别只看规则写了什么：查 `mapping.txt` 中对应匿名类是否还有 `beforeHookedMethod`（只剩 `<init>` = 已被删），或 `usage.txt` 是否把它列为删除项。装包验证用 `adb install -r --no-incremental`：默认的 Incremental Install（incfs 流式）会让 LSPosed 在开机早期读 APK 报 `Failed to open APK ... I/O error`，system_server 因此拿不到模块（长驻进程的模块代码要 reboot 才重载）。反射序列化的目标单独 keep：`JSON.toJSONString(ArrayList<Pair<Double,Double>>)` 靠 `first`/`second` 属性名，不 keep `kotlin.Pair` 会让路线导入导出解析失败。生效判据：`strings` dex 里调试字面量计数 0（常量折叠删掉恒 false 分支）、`mapping.txt` 中入口类未改名、`missing_rules.txt` 为空、`usage.txt` 删除项都是未用成员。坑：**重装模块后长驻进程（system_server 等）仍在跑旧模块代码**，日志里照旧出现 `[Portal][DEBUG]`——判「release 无 debug 日志」只认新启动进程（或第 7 步 reboot 后）的日志，别据长驻进程日志判定钳制失败。坑：重装 APK 后立刻 `am start` 可能报 `Error type 3: Activity class ... does not exist`，而 `pm path`、`dumpsys package` 的 Activity Resolver Table 都正常、App 其实已经起来了——用 `dumpsys activity activities | grep ResumedActivity` 或 logcat 里的窗口/`registerGnssStatusCallback` 日志确认，别据此判定装包损坏去重装。

14. GNSS 模拟效果排查（用户报「雷达 0G / 状态栏无定位图标」时）：先在模块日志确认 GNSS hook 装载——`[Portal] GnssLocationProvider done, status: N`（1=GnssLocationProviderImpl、2=GnssLocationProvider）；该行缺失才是该 ROM 找不到 provider 类，属设备差异而非 R8。卫星雷达与状态栏图标是客户端可见效果，取决于 `FakeLoc.enableMockGnss`（由 App 的 `start_gnss_mock` 指令在 system_server 置位），按第 9 步开调试日志抓 `registerGnssStatusCallback: injected!` 与 `onSvStatusChanged` 注入行，再判是「没开开关」还是「注入链路断」。完成：分别坐实 hook 已装载、开关状态、注入行三段。

15. 配置开关是否生效：受控 A/B——`adb shell date +%H:%M:%S` 记下点击时刻，点开关，`sleep 30` 后取最新 `modules_*.log` 按时间戳切出点击之后的 `[Portal][DEBUG]` 行（关→0 条即生效），并 pull 真实 prefs 核对落盘。**按进程分别统计**（`(system)`、`(com.android.phone)` 各算一份）。坑（既有 bug）：client 侧 proxy 拒收转发的 `put_config`（randomKey 每进程 lazy 生成、永不相等，日志 `Failed to handle instruction in <from>`），配置变更需重启该进程，别判「开关无效」。完成：按进程给结论并附证据行时间戳。

16. 装包落地与回退校验：`adb install` 的 `Success` **不代表包已更新到目标 user**（同版本号下 versionName 不变）——唯一可信校验是 `dumpsys package <pkg> | grep lastUpdateTime` 与 install 时刻核对，**先校验再 reboot**。回退某段 hook 后：reboot 后 `grep -c "<特征字面量>" modules_*.log` 应为 0，再按第 15 步 A/B 确认行为变了。完成：lastUpdateTime 落在本次 install 之后且回退特征计数为 0。

17. 模拟数据「未加工/不更新」与派生数学错排查：链路：权威状态（bearing/speed）→ 命令 → 注入字段 → 回调同步 → 传感器派生。①命令路径都更新权威状态（update_location 只改坐标→角度停滞，修：按位移算朝向）；②漏 `getLastLocation` 轮询；③冻结先看注入是否在跑（`listeners=N` 递增=在跑，`remaining=0` 后无新注册=停摆）；④注入端直写权威值→直线段锁死，改数据源层时间常数平滑+微扰；⑤过渡窗起点别用采样间隔倍数（1Hz 仍 2s）——`min(avgInterval,上限×0.5)` 夹硬上限；⑥角度忽然乱转=朝向更新基线太短（逐点跳点按相邻点算方向，噪声灌入 bearing）——改滚动参考点（≥3m）+ 转向速率限制 `setBearingSlew`，并置 `hasBearings=true`。指南针偏=派生数学错：Python 复刻 AOSP 验 compass==θ；`mX=+H·sinθ,mY=-H·cosθ` 恒偏 180°，改 `mX=-H·sinθ,mY=+H·cosθ,mZ=-H·dip`。完成：转向更新、直线段非零跨度、最稀疏采样过渡达标。

19. 回调改写验证与 hook 上限：放行注册才见真实类型（`result=true` 会掩盖，如磁力计 type=2）；有注册行无改写行 = 方法名不匹配或未记 handle→type；`dumpsys sensorservice` 的 `active-count` 判推流，`on-change`（step_counter）设备不动即零事件——纯改写驱动不了，换持续回调（位置回调）推进并投递给注册 listener，累加带小数（间隔<0.36s 时 `toLong()` 每 tick 加 0）。坑：逐实例装 hook 撞 Xposed 每类 64 次上限静默失效——对类装一次。
