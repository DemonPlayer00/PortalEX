# 传感器/位置模拟的统一架构（迁移方案）

> 状态：**迁移完成（2026-09-16）**：步骤①②③④ 均已落地并在真机跑通，六节验收清单逐项达成
> （数据见第六节）。本文是执行依据 —— 每轮改动
> 照这里的顺序与判据走，不靠对话记忆。第二段"迁移前现状"是既成事实，后面是待办与已落地记录。

## 一、目标（用户口径）

- **App 只当遥控器**：下发参数与数据、读回状态，**不持有任何模拟状态、不推进任何模拟逻辑**。
- **system_server 的钩子层是唯一的模拟世界**：体力、步频/步态、传感器事件、位置交付全在同一进程里，
  **钩子之间直接共享状态**（同一把世界锁 / 同一份结构），从而
  **消除跨进程通信开销与同步问题**。

## 二、迁移前现状（2026-09-16 实测）

| 谁 | 持有什么 | 位置 |
| --- | --- | --- |
| App | 体力状态机 + 参数、**路线/摇杆推进引擎**、每拍位移缩放 | `StaminaController`、`MockServiceViewModel.ensureMotionLoop` |
| system_server | 由交付位移反推速度、由速度推步频、native 世界合成全部传感器事件、位置交付改写 | `BaseLocationHook.injectLocation`、`BinderSensorMock` + `libportalsensor.so` |
| 交界 | `PUT_CONFIG`（50ms 推状态：速度/朝向/步数/开关/噪声档/步频倍率）+ 位置写回 | `ConfigSync` ↔ `RemoteCommandHandler` |

**问题**：同一个"世界"被切成两半 —— 体力在 App（受 Activity 生命周期影响，进程冻结就"停表"），
速度/步频在系统侧（只能**从位移反推**）。两边靠 50ms 的快照与"位移"这根细线同步。

## 三、目标架构

```
system_server（唯一世界，钩子间进程内共享）
  LocConfig + native 世界
    ├─ 体力状态机 + 参数         ← 本方案新增（原在 App）
    ├─ 路线/摇杆推进引擎         ← 本方案新增（原在 App 的 MockServiceViewModel）
    ├─ 步频/步态/传感器事件合成   ← 已有（BinderSensorMock + .so）
    └─ 位置交付改写              ← 已有（BaseLocationHook.injectLocation）
        ↑ 参数/路线数据（遥控指令）      ↓ 状态回读（status / remote prefs）
App（遥控器 + 普通客户端）
  · 设置页/体力页：写参数、显示回读状态
  · 路线编辑：产出路线数据并上传
  · 地图/标记：**像普通应用一样订阅 LocationManager**（顺带自证注入生效）
```

**一条硬约束（设计推出来的）**：位置流只能在**生成它的地方**被缩放，否则 App 的推进与交付流会越差越远、
路线终点永远走不到。所以"App 只当遥控器"必然要求**推进引擎也搬进系统侧** —— 这一步不能省，
省了就只能退回"App 执行器 + 模块状态"的折中（那仍是两层）。

- **回滚点**：迁移前状态 = `e4e960d`（栅格已移除、体力在 App）。任何一步出问题都可回到它。

## 八、已交付帧的两个**已知行为**（2026-09-17 真机配对抓帧后补记，勿当缺陷重查）

### 8.1 自动播放起步会把世界**瞬移**到路线起点

`MotionEngine.beat` 在 `playing && !snapped` 那一拍把位置直接摆到路线起点（只给坐标、不计位移，
以免凭空消耗体力）。若播放开始时世界不在这条路线上，客户端就会在两帧之间看到一个跳变 ——
真机实测两次分别是 **145 m / 170 m**。

**危害边界（已量化，故不修）**：
- 目标应用（步道乐跑）自己的离群点过滤会丢掉这次跳变 —— 它记录的总距离 **2.41 km** vs 我们
  路线全长 **2428 m**，差 **−0.7%**，说明那 170 m 没有进入它的里程；
- 因此实际损害只剩两处：**配速曲线上的第一根夸张尖峰**，以及被污染的单点统计
  （它的「最快配速」被写成 **0'35"/km** = 28.6 m/s，物理上不可能）。
- 该帧我们报的 `speed` 是**保底速度**（见 8.2），不是那个跳变对应的速度 ——
  给出 0.3 m/s 是当下能给客户端的最不坏信号（报真值会是一个荒谬的高速）。

**结论（用户裁决 2026-09-17）：不改，作为已知行为**。备选方案「把当前位置投影到路线上、
从最近路径点续跑」能彻底消除跳变且不伪造位移，但会把"把整条路线从头跑一遍"的语义
改成"从最近点续跑"，需要时再评估。

### 8.2 静止帧的速度是**保底噪声**，不是 0

会话开着但世界不动时，`location.speed` 报 `speedFloor` 附近的低通慢游走（默认 ~0.18~0.42 m/s），
**不是 0**。理由：真机语义下 `speed == 0` ⇒ `hasBearing()` 无意义，应用会放弃航向、指针归零
（实测步道乐跑就如此）。这块曾因**嵌在 `hasSpeedAccuracy()` 判断里**而在本 ROM 上整段失效
（静止帧实测恰好 0.0，客户端的配速被 0 除成锯齿），2026-09-17 已修（提交 `16cc65e`）。

### 8.3 运动期的速度噪声是**两尺度**的（会话偏置 + 秒级快分量）

注入速度 = 窗口实测速度 + 噪声，噪声自 2026-09-17（提交 `169bca0`）起为：
**每次会话一个固定偏置**（`LocConfig.enable` 的 false→true 沿抽一次，±0.5·`speedAmplitude`）
+ **OU 快分量**（τ=1.5 s、σ=0.2·`speedAmplitude`），合计钳在 ±`speedAmplitude`。

为什么不是逐帧独立的白噪声（旧实现）：客户端只要画**瞬时速度**，曲线必然是一片锯齿 ——
真机上就是这么看到步道乐跑配速曲线上那些 excursion 的（幅度落在 ±7% 白噪声 + 1 s 窗口锯齿的包络里），
而宽频噪声本身也不像真机（接收机的速度误差在一次跑步内基本是个固定偏置）。
静止保底速度（`speedFloorSample`）一直是"低通 + 慢游走"口径，这次把运动期补齐，两边统一。

⚠️ 因此：**同一会话内、同一段匀速，客户端读到的速度仍会与它的位移差分差一个恒定小量**（本会话实测 +0.115 m/s）。
这不是误差，是设计。

### 8.4 步事件的时间戳**不走全局单调钳位**（2026-09-21 修「两条步事件几乎同时」）

**现象**：客户端（含 1 秒轮询的普通计步应用）偶发看到两条步事件**几乎同时到达**，
按事件时间戳算步频/配速时会得到一个荒谬的瞬时值 —— 也就是"步数尖峰"。

**成因（原生自己的日志为证）**：步事件天生是"迟到"的 —— 它们的排定时刻落在**上一次推送的间隔里**
（空闲拍长时可达 1~2 秒），而这段时间里 IMU 通道早已以 20~66 ms 的节奏把**全局**游标
`g_last_emit_ts` 推到了"现在"附近。通用的 `jitter_ts` 有一条全局单调钳位
`ts = g_last_emit_ts + 1`，于是每条迟到的步事件都被粘成"上一条事件 + 1ns"：

```
step push delta=3 span=1000ms per=333ms      ← 1 秒里走了 3 步（正常）
step emitted gap=0ms 排定差=284ms（发出 …821 vs …822）  ← 排定差 284ms，发出只差 1ns ✗
```

**修法**：步事件改用**自己的**游标与最小间隔（`step_ts()`，见 `virtual_world.c`）：
排定时刻 + ±15 ms 抖动，且与上一条步事件**至少间隔 50 ms**，只保证"不越过 now"与"步流内部不回退"，
**不再与 IMU 的游标对齐**。这与真机一致 —— HAL 各传感器的 FIFO 相互独立，跨传感器的时间戳本就不保证有序，
客户端按同一传感器的 dt 计算。

**顺带修掉的第二个成因（计数器重基）**：短时间内涨的步数超过人类可达步频（阈值 12 步/秒）时，
那不是"走了这么多步"而是**基线被搬移**（会话重启接在真实计数器后面、宿主重放状态）。
旧行为会把它按 `span/delta` 排成一串事件（span 很短时 `per` 退化成 1ns ⇒ 几十条"同时"的步事件）。
现在只搬基线、不发事件，并记进 `step_diag` 的「重基跳过」计数。

**判据（两层，都进门禁/真机）**：

* host（`xposed/src/main/cpp/test/vw_step_timing_test.c`）：四个场景 —— 1 秒轮询 / 15 Hz 轮询 /
  边界轮询 / 计数器重基，断言**步流内部严格递增、无同刻对、最小间隔 ≥100ms**；
* 真机（Test 页「期望 1 秒更新间隔的监听器」+ 原生 `step_diag`）：修复前 180 秒长走抓到
  **2 对同刻**（都在会话起点）；修复后同条件 198 秒长走 **时间戳紧邻 0 次**，
  原生侧 `step emitted gap<100ms` 计数为 **0**。

⚠️ 判读口径：**送达同时 ≠ 事件同时**。框架会把攒下的事件一批交给应用，那时两条回调的送达时刻只差 0~2ms，
但事件时间戳可能差几百毫秒 —— 那是正常批量投递。真正的"两条同时"要看 **HAL 时间戳**（差 ≤5ms）。
第一版探针只看送达时刻，把正常批量也报成了异常。
